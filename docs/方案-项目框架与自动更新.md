## 1. 概述

MusicPlayer 是一个基于 .NET 10 与 Avalonia 的桌面音乐播放器。本方案定义的是**第一阶段的交付基线**，而不是播放器功能设计：一个可启动、可发布的空白首页应用骨架，加上基于 NetSparkleUpdater 与 GitHub Releases 的启动自动更新链路，并能在 GitHub 上一键产出首个正式版本。

一句话描述目标：用户双击运行 MusicPlayer 即可看到空白首页；应用在后台静默检查 GitHub Releases 上的 appcast，只有存在新版本时才提示用户；维护者通过 GitHub Actions 手动触发一次发布，即可得到 `MusicPlayer-win-x64-<version>.zip` 与 `appcast.xml`，并由 `releases/latest/download/appcast.xml` 这个稳定地址对外提供更新信息。

本阶段明确**不包含**播放内核、媒体库、插件体系、多平台安装包与 Ed25519 签名（签名给出升级路径，见第 9 章）。

## 2. 目标与范围

### 2.1 本轮目标

1. 建立可编译、可运行、可发布的 .NET 10 + Avalonia 应用骨架（空白首页）。
2. 集成 NetSparkleUpdater，启动后静默检查更新，有新版本时才走内置 UI 完成下载与安装。
3. 建立 GitHub Actions 发布链路：构建 → 打包 → 生成 appcast → 创建 Release。
4. 完成向 Public 仓库的首次发布，产出 v1.0.0 Release 与可访问的 appcast。
5. 本方案文档作为开发、评审、验收与安全审查的共同依据。

### 2.2 不在本轮范围

播放与解码、媒体库扫描、UI 设计系统、安装器（Inno Setup/MSIX）、代码签名证书、增量更新、macOS/Linux 分发、自动发布（每次提交触发）、应用内“检查更新”设置页（作为后续演进，见第 13 章）。

## 3. 技术选型与理由

### 3.1 运行时与 SDK

| 项 | 选择 | 说明 |
| --- | --- | --- |
| 运行时 | .NET 10 | 当前 LTS 版本，生命周期与工具链满足长期维护需要 |
| SDK | 10.0.401 | 本机已安装的 SDK 版本，直接用于本地构建与验证 |
| 目标框架 | `net10.0` | 与 SDK、依赖包 TFM 对齐 |
| 发布方式 | `win-x64` 自包含（self-contained） | 目标机器无需预装 .NET 运行时 |
| 分发形态 | zip 压缩包 | 免安装、便于后续升级替换；不写注册表、不需要管理员权限 |

选择自包含发布的原因是：更新链路要替换应用目录，自包含包的环境依赖最少，避免用户机器运行时版本差异导致更新后无法启动。代价是包体积较大（约数十 MB），在首版可接受。

### 3.2 UI 框架：Avalonia 11.3.9（而非 12.1.4）

这是本方案最关键的一个版本决策。

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| Avalonia 11.3.9 | **采用** | NetSparkleUpdater.UI.Avalonia 3.1.0 的 nuspec 在包括 `net10.0` 在内的所有目标框架组中，显式依赖 `Avalonia 11.3.9`、`Avalonia.Desktop 11.3.9`、`Avalonia.HtmlRenderer 11.3.0` |
| Avalonia 12.1.4 | 暂不采用 | 若主工程直接引用 12.1.4，NuGet 会把 Avalonia 统一提升到 12.x，而 NetSparkle 的 Avalonia UI 程序集是按 11.3.9 编译的，存在二进制不兼容与 XAML 运行时加载失败的风险；该组合未经官方支持 |
| NetSparkleUpdater 4.0.0-preview（对齐 Avalonia 12） | 暂不采用 | 预览版 API 与行为可能变化，不适合作为首个生产版本的依赖；待 4.0 正式版发布后再统一升级 |

结论：**主工程、Desktop、主题、字体等 Avalonia 相关包全部锁定 11.3.9**，形成单一版本面；升级 Avalonia 12 的动作与 NetSparkle 4.x 正式版升级合并为一次独立的技术演进。

### 3.3 更新框架：NetSparkleUpdater.SparkleUpdater + NetSparkleUpdater.UI.Avalonia（3.1.0）

| 包 | 版本 | 用途 |
| --- | --- | --- |
| NetSparkleUpdater.SparkleUpdater | 3.1.0 | 更新核心：appcast 拉取、版本比较、下载、签名校验、安装调度 |
| NetSparkleUpdater.UI.Avalonia | 3.1.0 | 内置 Avalonia UI：更新提示、Release Notes、下载进度 |

选型理由：

1. **TFM 直接可用**：3.1.0 的 `lib/net10.0` 目录下有 `NetSparkle.dll`，nuspec 也包含 `net10.0` 依赖组，无需降级目标框架或使用兼容层。
2. **能力匹配**：appcast + GitHub Releases 的静态托管模式天然契合；内置“后台静默检查，仅在发现更新时提示”的循环；支持跳过版本、稍后提醒。
3. **可演进到签名校验**：内置 Ed25519 校验与生成器，可在后续版本无痛切到严格模式。
4. **许可友好**：MIT，适合公开仓库分发。

代价：内置 UI 的版本节奏绑定 Avalonia 11.x（见 3.2），另外 Windows 下 zip 资产需要自定义安装步骤（见 6.4）。

### 3.4 依赖清单

| 包 | 版本 | 备注 |
| --- | --- | --- |
| Avalonia | 11.3.9 | 核心 |
| Avalonia.Desktop | 11.3.9 | 桌面后端 |
| Avalonia.Themes.Fluent | 11.3.9 | 主题 |
| Avalonia.Fonts.Inter | 11.3.9 | 字体 |
| NetSparkleUpdater.SparkleUpdater | 3.1.0 | 更新核心 |

### 4.2 工程约定

1. **csproj 关键属性**：`OutputType=WinExe`、`TargetFramework=net10.0`、`Nullable=enable`、`ApplicationManifest=app.manifest`、`AvaloniaUseCompiledBindingsByDefault=true`、`BuiltInComInteropSupport=true`。
2. **版本号单一来源**：`Version`、`AssemblyVersion`、`FileVersion` 三者与发布 tag 保持一致。首版为 `1.0.0` / `1.0.0.0` / `1.0.0.0`；发布时由 CI 以 `-p:Version=...` 注入，避免手工改文件导致版本漂移。
3. **运行时标识只在发布时指定**：日常 `dotnet build` 不固定 RID；发布使用 `-r win-x64 --self-contained`。
4. **NuGet 配置不入库**：根目录的 `NuGet.Config`（内网镜像 + 工作区包目录）属于本机环境文件，不提交、不修改、不删除。CI 使用默认 nuget.org；如未来 CI 需要固定源，另行提交仅用于 CI 的配置。
5. **构建前设置 `AVALONIA_TELEMETRY_OPTOUT=1`**：本地与 CI 都设置，避免 Avalonia 遥测写用户目录失败导致构建报错（MSB4018）。
6. **代码风格**：C# 使用文件范围命名空间、可空开启；XAML 与 code-behind 分离；更新相关代码只在 `UpdateService` 中出现。

## 5. 应用骨架（空白首页）

首版 UI 只承担“证明应用可运行、可发布”的职责：

- 单个主窗口，标题 `MusicPlayer`，默认尺寸 1000×680，最小尺寸 640×420，居中启动。
- 内容区为空白 `Grid`，仅右下角显示当前版本号（如 `v1.0.0`）；不放置播放控件、列表、菜单或占位文案，后续界面都放进这个 Grid。
- 使用 Fluent 主题与 Inter 字体，跟随系统明暗主题。
- `app.manifest` 声明 Windows 10/11 兼容性与 PerMonitorV2 DPI 感知，避免高 DPI 模糊。
- 不引入全局异常吞噬逻辑；启动路径上的异常应显式暴露，便于早期发现问题。

`UpdateService` 与 UI 的边界：窗口只负责在 `Opened` 事件里触发一次更新检查；`UpdateService` 内部完成 NetSparkle 的构造、启动、生命周期管理与异常兜底。UI 不直接引用 NetSparkle 类型，便于后续替换更新实现。

## 6. 启动检查更新时序

### 6.1 主流程

| 阶段 | 触发点 | 动作 | 失败时的行为 |
| --- | --- | --- | --- |
| 0 启动 | 用户运行 exe | Avalonia 初始化，显示主窗口 | 启动失败直接退出并记录日志 |
| 1 窗口就绪 | `MainWindow.Opened` | 通过 `Dispatcher.UIThread.Post` 投递更新初始化，避免阻塞首帧渲染 | 不影响窗口显示 |
| 2 初始化 | `UpdateService.Initialize` | 构造 `SparkleUpdater`：appcast 地址、`Ed25519Checker(SecurityMode.Unsafe)`、Avalonia `UIFactory`、`RelaunchAfterUpdate = true` | 捕获异常，记录日志，本次不检查 |
| 3 静默检查 | `StartLoop(doInitialCheck: true, forceInitialCheck: true, 24h)` | 后台拉取 appcast 并与当前程序集版本比较；无更新时全程无 UI | 网络错误/超时/解析失败均静默，等待下次启动或下一轮循环 |
| 4 发现新版本 | NetSparkle 循环 | 内置 Avalonia UI 展示版本号与 Release Notes，提供“下载 / 跳过此版本 / 稍后提醒” | 用户取消则本次结束，下次启动再提示 |
| 5 下载与校验 | 用户确认下载 | 下载 zip 到临时目录，校验长度；当前 `Unsafe` 模式不做签名校验；进度由内置 UI 呈现 | 触发 `DownloadHadError` / `DownloadedFileIsCorrupt`，告知用户，不重试 |
| 6 安装 | 下载完成、用户确认安装 | 抑制 NetSparkle 默认安装动作（原因见 6.4），由应用自身的替换流程在主进程退出后解压覆盖安装目录 | 替换失败时保留旧版本并提示手动下载，不做半覆盖 |
| 7 重启 | 替换完成 | 启动新版本 `MusicPlayer.exe`；旧版本退出 | 启动失败提示用户手动打开安装目录 |

### 6.2 “静默检查”的语义与 API 说明

NetSparkle 提供了两条容易混淆的路径，本方案明确取舍：

- `CheckForUpdatesQuietly`：文档明确“不显示任何 UI”，返回值需要调用方自行展示。若采用它，就必须自己实现提示窗口，与“复用内置 Avalonia UI”的目标冲突。
- `StartLoop(doInitialCheck, forceInitialCheck, interval)`：后台循环拉取 appcast 并比较版本，**只有确实存在更新时才通过 `UIFactory` 展示窗口**；首次启动时循环会先暂停数秒，避免应用刚打开就弹窗。

因此主路径使用 `StartLoop`。这也正好满足“静默检查、仅在有新版本时打扰用户”的产品要求。`StartLoop` 与 `CheckForUpdatesQuietly` 只能二选一，不得叠加，否则会出现重复下载与重复提示。首版不实现“检查更新”菜单项；后续若需要手动检查，使用 `CheckForUpdatesAtUserRequest`（会显示 UI）并复用同一 `SparkleUpdater` 实例。

其他约束：

- 同一个 `SparkleUpdater` 实例只能调用一次 `StartLoop`；重复调用会导致重复循环与重复弹窗。
- `UpdateService` 实现 `IDisposable`，在主窗口关闭或应用退出时停止循环并释放资源。
- 更新检查不能在 UI 线程同步等待网络结果。

### 6.3 边界行为

| 场景 | 约定 |
| --- | --- |
| DEBUG 构建 | 直接跳过更新检查（编译期条件），避免开发机被发布包覆盖 |
| 离线 / DNS 失败 / 代理异常 | 不弹窗、不抛出到 UI 线程，仅记录日志；不阻塞启动 |
| appcast 404 或格式错误 | 视为“无更新”，下次启动重试 |
| 安装目录不可写（如 Program Files） | 不执行自动替换，提示用户手动下载；见风险 R3 |
| 测试环境 | 环境变量 `MUSICPLAYER_APPCAST_URL` 非空时覆盖内置 appcast 地址，用于联调与私有源；正式分发包不设置该变量 |
| 退出时限 | NetSparkle 拉起的替换进程最多等待主进程 90 秒，退出流程必须在此时间内完成，退出前不做二次确认 |
| 重复提示 | 用户选择“跳过此版本”后，本地记录生效，同一版本不再提示；强制推广需递增版本号 |

### 6.4 Windows 下 zip 资产的安装落地（已采用：应用自接管）

NetSparkle 的默认安装器调度只识别 `.exe`、`.msi`、`.msp`；`IsZipDownload` 仅在 macOS/Linux 返回 true，**Windows 上的 zip 不会被自动解压执行**。因此本实现采用“应用自接管安装”，不依赖默认执行：

1. `UpdateService` 订阅 `InstallerProcessAboutToStart`（委托签名 `bool (Process process, string downloadFilePath)`），返回 `false` 抑制默认的“直接执行 zip”。
2. 下载完成后生成 `%TEMP%\MusicPlayer-apply-update.cmd`，以隐藏窗口启动，脚本内容为：
   - 用 `tasklist /FI "PID eq <pid>" /FI "IMAGENAME eq MusicPlayer.exe"` 等待旧进程退出，最多 60 秒；
   - 调用系统自带 `%SystemRoot%\System32\tar.exe -xf <zip> -C <安装目录>` 解压覆盖，要求 zip 根目录即 `MusicPlayer.exe`（不能多套一层文件夹）；
   - `start "" "<安装目录>\MusicPlayer.exe"` 重启应用，随后脚本自删；
   - 所有路径加引号，过程与错误写入 `%TEMP%\MusicPlayer-update.log`。
3. 主进程在事件处理返回 `false` 后通过 `Dispatcher.UIThread` 主动关闭，脚本才能覆盖文件；退出流程须在 90 秒内完成（NetSparkle 的等待上限）。
4. 安装目录必须当前用户可写（建议 `%LOCALAPPDATA%\MusicPlayer`），禁止 Program Files；更新配置 `update-state.json` 与日志 `logs/update.log` 也写在安装目录。
5. 已知限制：若解压失败（磁盘满、zip 损坏、文件被占用），脚本记录错误后仍会尝试启动应用，可能留下半更新目录。v1.0.0 接受该风险；后续改为 staging 解压后再替换，或改用 Inno Setup/MSIX 安装包回到 NetSparkle 原生安装器路径。

## 7. appcast 与版本比较

### 7.1 appcast 地址

默认地址固定为：

`https://github.com/Lwc-LiuWenCheng/MusicPlayer/releases/latest/download/appcast.xml`

`latest/download` 始终解析到“最新正式 Release”的同名资产，因此客户端不需要随版本改地址。前提是每次发布都把 `appcast.xml` 作为资产上传，并且不把草稿/预发布标记为 latest。

### 7.2 appcast 生成方式

由 `netsparkle-generate-appcast`（本机可用的 CLI 版本为 2.9.0）在 CI 中生成。关键参数：

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| `--single-file` | `MusicPlayer-win-x64-<version>.zip` | 单文件模式，只登记一个下载项 |
| `--file-version` | `<version>` | 显式指定版本，避免从文件名推断失败 |
| `-u` / `--base-url` | `https://github.com/Lwc-LiuWenCheng/MusicPlayer/releases/download/v<version>` | 资产下载前缀，最终 url 为 base-url + 文件名 |
| `-a` / `--appcast-output-directory` | `dist` | 输出目录 |
| `-n` / `--product-name` | `MusicPlayer` | 用于 appcast 标题 |
| `--link-tag` | appcast 地址 | 指向更新说明页 |
| `--key-path` | 密钥目录（仅签名阶段） | 见第 9 章 |

生成的 appcast 需包含：标题、link、单个 item（version、shortVersion、url、length、description/release notes）。发布前由 CI 做结构校验：版本号等于输入版本、url 指向本次 Release 资产、length 与 zip 实际大小一致。

### 7.3 版本比较规则

- NetSparkle 3.1.0 使用内置的 SemVerLike 做版本比较（不是 `System.Version`）：段数不同的版本按展开后的字典序比较，三段 `1.0.0` 会排在四段 `1.0.0.0` 之前。因此 appcast 写 `1.0.0` 不会比已安装的 `1.0.0.0` 更新，**不会误报**；appcast 写 `1.0.1` 时能正确判定为更新。已用本地 HTTP appcast 实测：1.0.0 无更新提示，1.0.1 弹出更新窗口。
- 下一个版本 `1.0.1`：csproj 的 `Version`/`AssemblyVersion`/`FileVersion` 与 tag `v1.0.1` 同步，appcast 标记 `1.0.1`；1.0.0 客户端判定为更新，1.0.1 客户端不再提示。
- `AssemblyVersion` 只接受 `Major.Minor.Patch.Revision` 四段数字；`Version`/`FileVersion` 允许预发布后缀，但首版统一使用纯数字三段，避免比较歧义。
- 发布前校验三方一致：git tag、csproj 版本、appcast 的 version；任一不一致即视为发布失败。
- 回退策略：不发布“降级”版本；如需撤回，只能发布更高版本号（如 1.0.2）覆盖。

## 8. 发布链路（GitHub Actions）

### 8.1 触发方式

`.github/workflows/release.yml` 使用 `workflow_dispatch`，输入参数 `version`（例如 `1.0.0`，不带前缀 v；tag 自动为 `v1.0.0`）。手动触发的理由：首版不引入“每次提交即发布”的风险，版本号由维护者显式决定。

工作流文件必须存在于默认分支才能被手动触发，这是首次发布的一个前置条件（见风险 R1）。

### 8.2 流水线步骤

| 步骤 | 内容 | 产出/校验 |
| --- | --- | --- |
| 1 检出 | `actions/checkout` | 源码 |
| 2 环境 | `actions/setup-dotnet` 安装 10.0.x；设置 `AVALONIA_TELEMETRY_OPTOUT=1`、`DOTNET_CLI_TELEMETRY_OPTOUT=1` | 可复现的构建环境 |
| 3 还原与构建 | `dotnet restore`、`dotnet build -c Release` | 编译通过 |
| 4 发布 | `dotnet publish src/MusicPlayer/MusicPlayer.csproj -c Release -r win-x64 --self-contained true -p:Version=<version> -o dist/publish` | 自包含产物 |
| 5 打包 | 生成 `MusicPlayer-win-x64-<version>.zip` | 资产文件 |
| 6 生成 appcast | `netsparkle-generate-appcast`（参数见 7.2），输出到 `dist` | `appcast.xml` |
| 7 产物校验 | 检查 zip 存在、appcast 版本/URL/length 正确 | 校验失败即中止 |
| 8 创建 Release | `gh release create v<version> --title ... --notes-file ... --latest`，上传 zip 与 appcast.xml | Release 页面与资产 |

说明：

- 生成 appcast 的工具可用 `dotnet tool install --global NetSparkleUpdater.Tools.AppCastGenerator` 安装；其运行需要 .NET 6/7/8/9 运行时之一，Windows runner 默认具备，必要时显式安装。
- Release Notes 优先读取仓库内按版本命名的变更说明文件；缺失时使用自动生成的说明，不阻塞发布。
- 发布成功后，工作流输出两个可点击地址：Release 页面与 `releases/latest/download/appcast.xml`。

### 8.3 权限与凭据

- workflow 顶层声明 `permissions: contents: write`，使用内置 `GITHUB_TOKEN`（`GH_TOKEN` 环境变量）创建 Release，不需要 Personal Access Token。
- 不使用第三方 Action 的可写令牌；不把任何密钥写入仓库文件。
- Secret 的创建与轮换只能人工在仓库设置中完成（见 9.2）。

### 8.4 幂等与失败处理

- 同 tag 已存在时 `gh release create` 会失败：重跑前需明确选择“删除旧 Release 重建”或“`gh release upload --clobber` 覆盖资产”，两者不可混用，避免半旧半新。
- 上传后做一次可达性校验：请求 `releases/latest/download/appcast.xml`，确认 HTTP 200 且内容版本号正确。
- 失败不回滚仓库内容，只重跑工作流；已发布版本的资产缺失用补传方式修复，不重新打 tag。

## 9. 签名策略

### 9.1 当前阶段（v1.0.0）：`SecurityMode.Unsafe`

首版使用 `Ed25519Checker(SecurityMode.Unsafe, ...)`，即不校验签名，安全性依赖 HTTPS 传输与 GitHub 仓库/账号权限。

- 适用理由：先打通“检查 → 下载 → 替换 → 重启”的完整链路，避免在密钥管理与 CI 注入尚未稳定时阻塞发布。
- 风险：若 GitHub 账号或 Release 资产被篡改，客户端无法识别，会安装被替换的包。
- 约束：该状态必须在 README 与本文档中明示；不得对外宣称“已签名/防篡改”。

### 9.2 升级到 Ed25519 严格校验的步骤

1. **生成密钥对**：执行 `netsparkle-generate-appcast --generate-keys --key-path <目录>`，得到 `NetSparkle_Ed25519.priv` 与 `NetSparkle_Ed25519.pub`（默认写入本地应用数据目录下的 netsparkle 子目录，可用 `--export` 打印）。私钥不入库、不写日志、不进构建产物。
2. **配置 GitHub Secret**：在仓库 Settings → Secrets and variables → Actions 新建 `SPARKLE_PRIVATE_KEY`，粘贴私钥全文。**MCP 工具没有创建/读取 secret 的能力，必须人工一次性配置**；配置完成后不要在聊天、文档或提交中回显。
3. **CI 注入并签名**：工作流把 Secret 写入临时密钥目录（或使用生成器支持的 `SPARKLE_PRIVATE_KEY` / `SPARKLE_PUBLIC_KEY` 环境变量），生成 appcast 时传 `--key-path`；同时上传生成器产出的 `.signature` 文件（若启用签名文件模式）。
4. **应用切严格模式**：把公钥写入应用（常量或嵌入资源），`Ed25519Checker` 改为 `SecurityMode.Strict` + 公钥；不再保留 `Unsafe` 分支。
5. **验证**：篡改 zip 或 appcast 签名后，客户端必须拒绝安装并给出提示；正常包必须能通过校验并完成更新。

### 9.3 密钥治理

- 私钥仅存于 GitHub Secret 与离线安全备份；任何情况下不进入仓库历史。
- 轮换流程：先发布内置“新公钥”的版本并确保用户升级，再切换 CI 签名密钥；顺序颠倒会导致存量客户端校验失败。
- 私钥丢失：只能通过发布内置新公钥的版本重建信任链，旧版本用户需手动升级一次。

## 10. 环境约束与已知限制

| 约束 | 影响 | 应对 |
| --- | --- | --- |
| 本机沙箱内直连 HTTPS 失败（schannel） | 本地无法访问 GitHub、无法执行 git 远端操作、无法下载 Release 资产 | GitHub 相关操作全部通过 MCP 完成；本地只做构建与静态校验 |
| NuGet 走内网 NuGet 镜像 | 依赖还原依赖本机镜像配置 | 根目录 `NuGet.Config` 仅作本机环境文件，不提交、不改动；CI 使用 nuget.org |
| appcast 生成器本地不可用 | 生成器默认写本地应用数据目录，受沙箱写权限限制 | appcast 一律由 CI 生成；本地只核对参数与产物结构 |
| NetSparkle 不支持 `file://` appcast | 本地用文件路径联调会报 “The 'file' scheme is not supported” | 本地联调改用本地 HTTP 服务（`http://localhost:<端口>/appcast.xml`）；线上始终用 https |
| Avalonia 遥测写用户目录受限 | 构建可能以 MSB4018 失败 | 构建前设置 `AVALONIA_TELEMETRY_OPTOUT=1`（本地与 CI 都设置） |
| GitHub 凭据能力有限 | MCP 不能创建 secret、可能缺少 workflow 文件写入权限 | 需要人工一次性补配置；见风险 R1、R7 |
| 无代码签名证书 | Windows SmartScreen 可能提示未知发布者 | 首版接受提示；后续申请代码签名证书 |

需要强调：CI runner 的网络与权限模型与本地沙箱完全不同，不要把本地的网络限制写进工作流，也不要因为本地无法直连而放弃 CI 侧的联网步骤。

## 11. 风险与回滚

| 编号 | 风险 | 影响 | 应对 | 回滚 |
| --- | --- | --- | --- | --- |
| R1 | CI/工具令牌缺少 workflow 权限，无法写入 `.github/workflows/release.yml` 或触发工作流 | 无法自动发布 | 用 MCP 完成仓库与文件发布；工作流文件由具备 `workflow` 权限的人工提交或网页创建；先在默认分支落地再触发 | 工作流文件保留但不触发；不影响已发布版本 |
| R2 | Release 资产缺失或 appcast 未上传 | 客户端检查静默失败，用户收不到更新 | 发布后校验 `latest/download/appcast.xml` 返回 200；CI 内校验资产清单 | 用 `gh release upload --clobber` 补传；必要时重跑工作流 |
| R3 | 安装目录不可写（安装在 Program Files 或受控目录） | 自动替换失败，更新中断 | 默认安装到用户目录（如 `%LOCALAPPDATA%\MusicPlayer`）；更新前做写权限探测，不可写则降级为“提示 + 手动下载” | 保留旧版本不删除；提示用户手动解压覆盖 |
| R4 | 开发者在 `bin/` 目录运行发布版并点击更新，导致开发目录被替换 | 开发环境被破坏 | DEBUG 构建跳过检查；发布版检测安装标记文件，非安装目录时禁用自动替换 | 重新构建；从源码恢复 |
| R5 | Windows 下 zip 无法被 NetSparkle 默认安装（技术限制） | 用户点“安装”无效果或报错 | 按 6.4 抑制默认安装并实现自定义替换；若后续移除自定义逻辑，则降级为手动下载 | 回退为“仅提示下载、不自动替换”，并在 Release Notes 说明 |
| R6 | 版本号不一致（tag / csproj / appcast） | 不提示更新，或错误提示 | CI 强制校验三者一致，不一致即失败 | 删除错误 Release 与 tag，重新发布正确版本号 |
| R7 | Ed25519 私钥 Secret 未配置或配置错误 | 签名阶段失败，或客户端校验失败 | 升级签名前先在测试 tag 上验证；Secret 配置由人工 double-check | 临时回退 `Unsafe` 并重新发布，随后修正密钥 |
| R8 | 用户离线、代理拦截或 GitHub 访问不稳定 | 检查失败，无提示 | 全部异常吞掉并记录日志，下次启动重试；不阻塞启动 | 无需回滚；不影响本地功能 |
| R9 | `Unsafe` 模式下资产被篡改 | 安装恶意包 | 尽快按第 9 章升级 Ed25519；发布页开启 2FA 与分支保护 | 发现后立即发布更高版本并公告，建议用户手动重装 |
| R10 | MCP 发布过程中断（网络或权限） | 仓库内容不完整或 Release 缺失 | 发布前在本地整理文件清单；发布后逐项核对目录与资产 | 重新执行发布步骤；已存在文件按需覆盖 |

统一原则：**更新失败永远不能破坏现有安装**。替换前先完成下载与校验，替换时保留回退路径，失败即停在旧版本并给出可操作的提示。
